# hch zsh completion: design

## Intent

Tab completion for `hch` in zsh, so commands and their flags can be completed instead of remembered. It loads the same way the other completions on this machine do: `source <(hch completion zsh)` in `.zshrc`.

## Goals

- `hch <TAB>` offers `where`, `version`, `up`, `help` and `completion`, each with its one-line description from `hch help`.
- After a command, `--<TAB>` offers only the format flags that command accepts: `--json`, `--table` and `--markdown` for `where` and `version`, `--json` alone for `up`. Once one format flag is on the line, the others aren't offered, because they're mutually exclusive.
- `-h` and `--help` are offered.
- `hch completion <TAB>` offers `zsh`.
- The completion script is generated from the same command table that drives parsing and `USAGE`, so adding a command or flag updates the help and the completions together.

## Non-goals

- No bash or fish completion yet. The `completion <shell>` shape leaves room for them later.
- No install step that edits `.zshrc` or writes into `fpath`. The README tells the user which line to add.

## Approaches

1. **Generated by a `hch completion zsh` command (chosen).** Prints a `#compdef hch` script built from the command table. It can't drift from the code and matches how `ng` completion is already loaded here. Chosen by Matt.
2. **Static `_hch` file in the repo, added to `fpath`.** Needs its own install step and has to be updated by hand whenever a command or flag changes.
3. **Dynamic completion that calls back into `hch` on every TAB.** Overkill for a fixed set of commands and flags, and slower on each keypress because Bun starts up every time.

## Design

- Each entry in the `commands` table in `src/cli.ts` gets a `description`. `help` and `completion` appear in the table too, or alongside it, so `USAGE` and the completion script both read every command from one place. `USAGE` keeps its current text.
- `completion` takes one positional argument, the shell name. With no shell, or a shell other than `zsh`, it's a usage error (exit 2) naming the supported shells. It takes no format flags.
- `src/commands/completion.ts` exports a pure function that builds the zsh script from the command list (names, descriptions, accepted formats). Unit tests check the script beside it.
- The script uses `_arguments` with a `->command` and `->args` state: `_describe` for the commands, then per-command flag specs with exclusion groups so only one format flag is offered.
- `src/cli.test.ts` covers `hch completion zsh` (exit 0, output starts with `#compdef hch`), a missing shell and an unknown shell (exit 2 and the message).
- A live check in zsh: load the script with `compinit` and confirm the completions, for example with `zpty` or by checking that `_hch` is defined and `zsh -n` accepts the script.
- The README gets a "Completions" section with the `source <(hch completion zsh)` line, placed after `compinit`. `hch help` lists the `completion` command.

## Left to the builder

- The exact `_arguments` spec strings and how the script lays them out.
- Whether `help` and `completion` live in the `commands` table or in a small list beside it, as long as there's one source for names and descriptions.
